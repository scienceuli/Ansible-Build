# VFLL WordPress on gauss

`https://lektorenverband.de` (VFLL blog) on gauss (`gauss.science-and-more.com`,
152.53.138.19, netcup, ARM). Moves from a hand-made docker compose stack on
Debian 12 to a fresh Debian 13 with Ansible-managed containers: the old stack
ran a WordPress image built 2025-09 and never rebuilt (PHP 8.3.25, vulnerable
to the PHP RCEs of 2026-10-21 - see [../php_patching/README.md](../php_patching/README.md)).

## Old stack (until the reinstall)

`/srv/wordpress/vfllwp` (compose project `vfllwp`, from a git repo):

| Container | Image | Data |
|---|---|---|
| `nginx-proxy` + `nginx-proxy-acme` | `jwilder/nginx-proxy:alpine`, `nginxproxy/acme-companion` | `./certs`, `./nginx/vhost.d` |
| `wordpress` | `vfllwp_wordpress` (`FROM wordpress:latest`) | bind mount `./wordpress/wp-content` (2.5 GB, 2.4 GB uploads); core inside the image |
| `wp_db` | `mysql:8.0` (EOL 2026-04) | bind mount `./database` |

Credentials in `.env` (they leaked into a Claude session log on 2026-10-21 -
the new stack uses new ones). Nightly root cron `/srv/backups/backup_vfllwp.sh`
dumps to `/mnt/storagespace/vfllwp` - **on the same disk**, gone with the
reinstall.

## New stack

All containers on the docker network `science-and-more.com`:

| Container | Image | Data | Role |
|---|---|---|---|
| `nginx01` + `certbot01` | `nginx_image`, `certbot/certbot` | `/usr/share/nginx01`, `/usr/share/certbot01` | `nginx`, `certbot` - only published ports (80/443) |
| `wordpress01` | `wordpress:php8.3-apache` | volume `wordpress_data01` → `/var/www/html` (core, `wp-config.php`, `wp-content`) | `wordpress` |
| `gauss-mysql01` | `mysql:8.4` | volume `mysql_data01`, `/usr/share/gauss-mysql01/my.cnf` | `mysql` (dependency of `wordpress`) - name `{{ inventory_hostname }}-mysql01`, unique across servers for monitoring |

| URL | Goes to |
|---|---|
| `https://lektorenverband.de` | `wordpress01:80` (500 MB uploads, 300 s timeout) |
| `https://www.lektorenverband.de` | 301 → `https://lektorenverband.de` |

- The image tag pins the **PHP branch**; WordPress core lives in the volume and
  updates itself (auto updates / admin). The image is pulled on every run
  (`wordpress_pull`), so rebuilt images bring PHP fixes.
- `wp-config.php` is generated by the image from the `WORDPRESS_*` env on the
  first start (new salts → everyone is logged out once). It honours
  `X-Forwarded-Proto` from nginx01, so WordPress sees https.
- Backups: restic, 02:xx nightly - `mysql-dump` of `gauss-mysql01/wordpress` and
  the volumes of `wordpress01`, to `backup.science-and-more.com/gauss`.

## Configuration

| File | What |
|---|---|
| `inventories/hosts.yml` | gauss in `debian13` and in group `wordpress` |
| `inventories/host_vars/gauss/wordpress.yml` | mysql + wordpress role vars (images, names, DB); `mysql_hostname` is referenced everywhere else (`wordpress_db_hostname`, `restic_backup_set`, `restore.yml`) |
| `inventories/host_vars/gauss/wordpress_vault.yml` | `vault_wordpress_mysql_root_password`, `vault_wordpress_db_password` (generated 2026-10-21) |
| `inventories/host_vars/gauss/vars.yml` | `nginx_proxies`, certbot, `restic_backup_set` |
| `playbooks/wordpress.yml` | deploys gauss-mysql01 + wordpress01 (any host in group `wordpress`) |
| `backup.yml` | backup of the **old** stack → `~/Backups/gauss-vfllwp/<date_time>/` on the controller |
| `restore.yml` | newest (or `-e vfllwp_backup_name=…`) backup → new stack |

A backup contains `wordpress.sql.gz` (mysqldump `--single-transaction`),
`wp-content.tar`, `project-config.tar.gz` (old compose files, `.env`, certs,
scripts, `.git`), `site-info.txt` (versions, URLs, post/comment/user counts)
and `SHA256SUMS` (verified on the controller after the download).

## Reinstall, step by step

From the repo root (`~/Devel/Ansible-Build`), so `ansible.cfg` and
`.vault-pass` are found.

**1. Final backup** - right before the reinstall, after a content freeze
(tell the editors: no new posts/comments from now on). `wp_db` must run, the
`wordpress` container may be stopped. Needs ~3 GB free on the controller
(checked by the playbook).

```sh
uv run ansible-playbook -i inventories playbooks/vfll_wordpress/backup.yml
ls -l ~/Backups/gauss-vfllwp/
```

Optional second copy (the Mac disk is nearly full), e.g. to a USB disk or
`scp -r ~/Backups/gauss-vfllwp/<date_time> backup.science-and-more.com:`.

**2. Reinstall** gauss in the netcup SCP: Debian 13 (trixie) image, your SSH key
for root. The IP stays 152.53.138.19, DNS (`lektorenverband.de`, `www`) needs
no change. Then forget the old host key:

```sh
ssh-keygen -R gauss.science-and-more.com
ssh root@gauss.science-and-more.com true    # accept the new key
```

**3. Base setup** (like joule, [README](../../inventories/host_vars/joule/README.md)):

```sh
# as root: packages, users, sudo
uv run ansible-playbook -i inventories playbooks/bootstrap.yml -l gauss
# Docker (dependency of docker_network) - setup.yml needs it
uv run ansible-playbook -i inventories playbooks/setup.yml -l gauss -t docker_network
# baseline: timezone, cron, maintenance, restic, ufw (22/80/443), iam ...
uv run ansible-playbook -i inventories playbooks/setup.yml -l gauss
```

`restic : Check restic repository` fails once with *repository does not
exist* (`...ignoring`) - the next task creates `backup.science-and-more.com/gauss`.

**4. WordPress + MySQL**

```sh
uv run ansible-playbook -i inventories playbooks/wordpress.yml -l gauss
```

Don't open the site yet - without nginx01 it isn't reachable anyway, and the
empty install would offer the setup wizard.

**5. Restore**

```sh
uv run ansible-playbook -i inventories playbooks/vfll_wordpress/restore.yml
```

Pushes the newest backup to `/var/tmp/vfllwp-restore/` (checksums verified
again), stops wordpress01, replaces the database and `wp-content`, starts
wordpress01, runs `wp core update-db` (wp-cli in a throwaway `wordpress:cli`
container) and asserts siteurl/home = `https://lektorenverband.de` and the
number of published posts against `site-info.txt`. A marker
(`/var/tmp/vfllwp-restore/.restored`) prevents a second run from overwriting
the site; `-e vfllwp_force=true` restores again (**drops the database**).

**6. Proxy + TLS** (port 80 must reach gauss for the HTTP-01 challenge;
`nginx_resolver` is set, so nginx01 also starts while wordpress01 is down):

```sh
uv run ansible-playbook -i inventories playbooks/proxy.yml -l gauss
```

**7. Backup jobs**

```sh
uv run ansible-playbook -i inventories playbooks/setup.yml -t restic -l gauss
```

**8. Check**

```sh
uv run ansible-playbook -i inventories playbooks/php_patching/check.yml -l gauss
curl -sI https://lektorenverband.de/ | head -1
curl -sI https://www.lektorenverband.de/ | grep -i location
```

In the browser: front page, a few posts with images, admin login (all users
must log in again), Plugins → updates (at the rehearsal: MailPoet,
host-webfonts-local, Yoast SEO had updates), MailPoet sending, Settings →
Permalinks once "Save" if posts 404. Compare `site-info.txt` with the admin
counts.

## Rehearsal (2026-10-21)

Restore of the backup `2026-10-21_1658` in throwaway containers on the old
gauss (`mysql:8.4` with the role's `my.cnf`, `wordpress:php8.3-apache`,
isolated network): dump imported in 36 s, `core update-db` 6.8.11 → 7.1.3
(db version 60421 → 61833), siteurl/home correct, 479 published posts, all 12
active plugins load, front page HTTP 200 (76 KB).

It found a bug in the `mysql` role: `log_error = /var/log/mysql/error.log` in
`my.cnf` made mysqld abort in the official `mysql:8` images (the directory
doesn't exist) - removed, the error log goes to `docker logs`.

## If the new install fails

The old disk is gone, but `project-config.tar.gz` has the complete old compose
project: unpack it to `/srv/wordpress/vfllwp`, unpack `wp-content.tar` there
with `tar -C wordpress -xf wp-content.tar`, copy `wordpress.sql.gz` to `./mysqldumps/backup.sql.gz` (the
old compose file imports it on the first start of an empty `./database`) and
`docker compose up -d --build`. That brings back the old, vulnerable stack -
only as a stopgap.
